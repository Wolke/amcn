## 1. 為什麼要改

三台機器的試點在半天內找到四個真實缺陷（#40 無重連、#41 匯出成長、#42 無時間戳、#43 無跨平台診斷），這證明「真的跑起來」有價值。但它同時暴露實驗設計的問題：

**證據取得要靠人。** 情境 A（斷 M3 網路）的結論是「panel 沒有自己回來」，但**無法分辨是行程死了還是卡住了**——那個差別只寫在 M3 的終端機上，而我看不到。我後續用兩個隔離測試排除了重連邏輯（單一 verifier 在 Hub 消失 25 秒後自行恢復）與 UDP beacon 搶埠（三個同機 verifier 全部 3/3 重連），但「M3 當時發生什麼」已經永久無法回答了——現場沒了。

**人工操作本身製造噪音。** 半天內：M3 的 IP 變過兩次、panel seed 換過一次（押注因此被棄置）、M3 睡著兩次、M2 的 `hubHost` 停在佔位 IP 二十分鐘、我自己兩次用過寬的 `pkill` 誤殺試點 Hub。每一次都要幾輪對話才排除，而且每一次都改變了現場。

**最重要的：想測的故障測不到。** 情境 A 想驗「靜默中斷造成半開 socket」，但關 Wi-Fi 時 OS 送出了 RST，Hub 兩秒就偵測到——等於乾淨關閉。要重現真正的靜默中斷需要防火牆規則（root）或物理拔線，而「程式裡一處 `setKeepAlive` 都沒有」這個風險**至今未被驗證**。

## 2. 槓桿：W10 剛抽出來的 ITransport

故障注入不需要虛擬機、不需要 root、不需要真實網卡——它需要的是一個可以攔截的縫，而 W10 為了可替換性剛好抽出了那個縫（`lib/transport.js`）。在那一層可以注入的東西，正好覆蓋我們想測的故障：

| 故障 | 真實對應 | 現在能不能測 |
|---|---|---|
| `blackhole` 收下但不送達、永不關閉 | 拔網路線、防火牆丟包、機器凍結 | **這就是情境 A 沒測到的那個** |
| `reset` 立即硬斷 | 關 Wi-Fi、對方進程被 kill | 情境 A 實際測到的 |
| `latency` / `jitter` | 跨機延遲、Wi-Fi 抖動 | #36 就是這一類（1500ms 寬限期在真實延遲下卡住）|
| `loss` 隨機丟 N% frame | 擁塞、弱訊號 | 未測 |
| `freeze` TCP 活著但應用層不讀 | 進程卡死、swap、GC 暴衝 | 未測，而且 keepalive 救不了這種 |
| 單向中斷 | 非對稱路由、單向防火牆 | 未測，最難用人工重現 |

## 3. 分階段

### Phase 1：`lib/transport-chaos.js`

包裝任一底層傳輸（tcp／http），由**執行期可改的控制檔**驅動（`AMCN_CHAOS=path.json`，每 200ms 輪詢），所以情境腳本能在跑到一半時翻轉故障，不必重啟任何行程。

控制檔形狀：

```jsonc
{ "mode": "blackhole",        // blackhole | reset | latency | loss | freeze | none
  "direction": "both",        // in | out | both  ← 單向中斷
  "latencyMs": 250, "jitterMs": 100, "lossPct": 5,
  "match": "127.0.0.1:47180"  // 只對某個對端生效
}
```

刻意做成獨立實作而不是改 tcp/http：`demo-transport.js` 斷言「兩種傳輸產生同一本帳」，混進故障邏輯會讓那個保證失去意義。chaos 是第三個實作，包在另外兩個外面。

### Phase 2：`lib/invariants.js`

把已經散在四支 demo 裡、各自只檢查一部分的斷言抽成可重複呼叫的函式：Σ=0、雜湊鏈可離線重驗、每筆 quorum 收據都有可歸責的 attestation、`list_verifiers` 不得包含已離線者、結算延遲上界、沒有合約卡住超過 T。

差別在**連續檢查**：現在每支 demo 在結尾檢查一次，故障情境需要的是「整個過程中不變式從未被破壞」。

### Phase 3：`chaos-run.js <scenario.json>`

一個指令跑完：拉起拓撲（Hub＋N 個 agent＋panel）→ 依時間表注入故障 → 持續取樣不變式（沿用 `drill-watch.js` 的形狀）→ 輸出時間軸報告與 PASS/FAIL。帶 `--seed` 讓失敗可重播。

首批情境，每一個都對應一個已知或懷疑的缺陷：

| 情境 | 注入 | 要回答的問題 |
|---|---|---|
| `panel-blackhole` | panel 的連線靜默中斷 3 分鐘 | Hub 多久才發現？期間 pool 是否宣告死掉的 verifier？（**keepalive 缺失的實證**）|
| `panel-freeze` | verifier 行程 SIGSTOP | TCP 活著但不回應——keepalive 也救不了，Hub 有沒有任何防線？ |
| `panel-death` | 行程被殺且不重啟 | 對應 M3 那次：確認「行程死了就不會回來」並量化後果 |
| `hub-kill-takeover` | Hub 消失 → 待命 Hub 以匯入接手 | 就是 W10 演練，但全自動、可重播 |
| `hub-blackhole` | Hub 靜默消失（非 kill） | client 端要多久才放棄那條連線 |
| `flaky-link` | 5% 丟包＋200ms±100ms 抖動，跑 10 分鐘 | #36 那一類的殘餘問題 |
| `one-way` | 只斷 Hub→panel 方向 | 最難人工重現的一種，也最容易產生「雙方都以為對方活著」|

### Phase 4：W11 紅隊接上來

紅隊盤點的 59 案裡，可自動化的 50 案大半就是故障或對手注入。`chaos-run.js` 的情境格式直接當紅隊案例的載體，`known-open` 的 13 案斷言「行為與登記簿一致」。等於 W11 不需要另一套工具。

## 4. Owner 裁定：開發迴路中不留人工環節（v2）

原本這一節列出「真實機器才能做的事」，並把三台機器留在開發流程裡。Owner 裁定移除：**凡是需要人工操作才能推進的環節，一律不放進開發計畫**。理由是實測出來的——半天裡人工環節貢獻的不是證據，是噪音與不可重現的現場（§1）。

因此三台機器試點**退出開發迴路**。它不是被否定，是被改變定位：以後它只在功能完成、chaos 情境全綠之後，作為一次性的「真實環境確認」，而且那次確認不阻擋任何開發工作。

### 原本要靠真實機器的四件事，改成這樣處理

| 原本 | 現在怎麼做 | 誠實差距 |
|---|---|---|
| OS 睡眠／喚醒 | chaos 提供兩種變體：`reset`（睡眠時 OS 幫忙關 socket，實測就是這個）與 `blackhole`（靜默消失）。行程層面用 SIGSTOP／SIGKILL 模擬卡死與死亡 | 真實睡眠可能同時發生時鐘跳躍與網路重新協商；分開注入測得到，組合起來的交互作用測不到 |
| 真實 DHCP 換位址 | 情境中把 Hub 搬到另一個埠／位址並重新廣播 beacon，client 必須自行跟隨 | 換的是埠而非網段；跨網段的路由變化測不到 |
| 跨機時鐘偏移 | chaos 新增 `clockSkewMs`，對送出的 frame 時間戳加偏移，直接打 beacon 的 60 秒容許窗 | 只偏移訊息時間，不偏移行程自己的 `Date.now()`；純本機的時間計算不受影響 |
| 牆上時鐘 soak | 無人值守情境跑數小時，自動取樣記憶體／句柄／檔案成長 | 與真實機器等價，只是跑在同一台上——共用資源的干擾測不到 |
| **跨 OS 行為** | **無法模擬，接受這個缺口** | Windows 的 socket 語義、PowerShell、防火牆預設值測不到（#32／#43 都出自這條）。緩解方式只有兩個：不寫 OS 專屬程式碼路徑，以及把 Windows 差異留在文件裡 |

### W10 演練的定位

§5 仍然把它列為不可砍，這份文件不推翻那個裁決。改變的是**順序**：故障先在 chaos 情境裡被找到與修好，真實演練退到最後當確認。它不該是我們第一次看到缺陷的地方——而目前為止它一直是。

## 5. 全自動執行迴路

開發、部署、測試、運行由本專案的工具鏈自行完成，不需要人在場：

1. **拓撲由程式拉起**：`chaos-run.js` 自己 spawn Hub、N 個交易 Agent、panel、canary，跑完自己收乾淨。埠位從 offset 導出，可與任何東西並存。
2. **故障由時間表注入**：情境檔宣告「T+30s 靜默中斷 panel 連線 120s」，不需要有人拔線。
3. **判定由不變式自動完成**：`lib/invariants.js` 全程連續檢查，違反即記錄時間點與現場（匯出檔存檔），失敗可用 `--seed` 重播。
4. **回歸由 demo 套件守門**：六支 demo（21／12／6／7／8／7）＋模擬器 21 tests 在每次修改後跑。
5. **發現的缺陷自己進登記簿**：與 #40／#41／#42／#43 相同格式，寫明「怎麼發現、修法、沒涵蓋什麼」。

人工只保留一個位置：**裁決**。經濟參數（如 #1 的 25 vs 50 CC）、範圍取捨、是否偏離 §5 這類決定仍然要 Owner 拍板，但那是幾句話的事，不是操作。

## 6. 立即順序

1. `lib/transport-chaos.js`＋`panel-blackhole` 情境——補上情境 A 沒測到的靜默中斷，大概會直接給出一個 keepalive 相關的 P1
2. `lib/invariants.js`——把四支 demo 各自檢查一次的斷言抽成連續檢查
3. `chaos-run.js`＋其餘七個情境（見 §3 Phase 3 表）
4. 修掉情境找到的缺陷，登記
5. 接 W11：59 案裡可自動化的 50 案改寫成情境
6. 無人 soak（數小時），量成長與洩漏
7. 全綠之後，才排真實三台的一次性確認

## 7. 驗收目標：第一個可運行版本（Owner 裁定）

Owner 只在**驗收**時進場，而驗收環境是「多台機器、不同地點」。這不是同一個區網多開幾台——它改了需求，因為跨地點意味著流量經過公網：

| 目前狀態 | 跨地點需要什麼 | 登記 |
|---|---|---|
| 傳輸層無加密，metadata 明文 | TLS（或等效）——否則 §16 威脅 9 對路徑上任何人敞開 | **#44 P1** |
| 發現與輪替＝區網 UDP 廣播 | 跨網段可用的 rendezvous，否則搬移 Hub 又回到每台手改設定 | **#45 P1** |
| Agent 只出站連 Hub（§2.2）| 這一項本來就沒問題——NAT 後的 Agent 不需要穿透，只有 Hub 需要可達位址 | — |
| 時間常數以本機延遲校準（#36 的 1500ms、選標 500ms 視窗）| 跨地點 RTT 50–200ms，這些常數要重新校準；chaos 的 `latency`／`jitter` 就是為此 | 待量測 |
| 時鐘偏移 | beacon 的 60 秒容許窗要真的被跨機時鐘測試；chaos 的 `clockSkewMs` 可注入 | 待量測 |

所以「第一個可運行版本」的定義收斂成：

1. §20 十項驗收在**跨地點**拓撲上成立（不是區網）
2. #44 傳輸加密、#45 跨網段發現輪替 已交付
3. 時間常數在 WAN 延遲下校準完成，chaos 的 `wan` profile 全綠
4. 六支 demo＋模擬器 tests＋全部 chaos 情境 綠燈
5. 部署是一條指令：Owner 在每台跑同一個指令、填一個位址與 pin，不需要逐檔編輯

第 5 點是從這半天學到的——`hubHost` 停在佔位 IP 二十分鐘、seed 換掉導致押注被棄置、`maxUnitsPerTask` 要手改，這些都是驗收時會再發生一次的摩擦。驗收前必須收乾淨。

chaos 的開發預設 profile 因此不是 localhost，而是 **`wan`**（延遲 80ms±40、丟包 1%、偶發單向中斷）。用真實世界的條件開發，而不是開發完才發現常數是為 localhost 調的——#36 就是那樣被找到的。
