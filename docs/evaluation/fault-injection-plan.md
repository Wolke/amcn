# 故障注入計畫：把發現缺陷的工作從人手上搬走

| 欄位 | 內容 |
|---|---|
| 文件 | 開發計畫修正：以自動故障注入取代人工拔線 |
| 日期 | 2026-09-16 |
| 起因 | 三台機器試點的實測經驗（見 §1） |
| 影響 | W11 紅隊的執行方式、W10 拔線演練的定位 |

---

## 1. 為什麼要改

三台機器的試點在半天內找到四個真實缺陷（#40 無重連、#41 匯出成長、#42 無時間戳、#43 無跨平台診斷），這證明「真的跑起來」有價值。但它同時暴露實驗設計的問題：

**證據取得要靠人。** 情境 A（斷 M3 網路）的結論是「panel 沒有自己回來」，但**無法分辨是行程死了還是卡住了**——那個差別只寫在 M3 的終端機上，而我看不到。我後續用兩個隔離測試排除了重連邏輯（單一 verifier 在 Hub 消失 25 秒後自行恢復）與 UDP beacon 搶埠（三個同機 verifier 全部 3/3 重連），但「M3 當時發生什麼」已經永久無法回答了——現場沒了。

**人工操作本身製造噪音。** 半天內：M3 的 IP 變過兩次、panel seed 換過一次（押注因此被棄置）、M3 睡著兩次、M2 的 `hubHost` 停在佔位 IP 二十分鐘、我自己兩次用過寬的 `pkill` 誤殺試點 Hub。每一次都要幾輪對話才排除，而且每一次都改變了現場。

**最重要的：想測的故障測不到。** 情境 A 想驗「靜默中斷造成半開 socket」，但關 Wi-Fi 時 OS 送出了 RST，Hub 兩秒就偵測到——等於乾淨關閉。要重現真正的靜默中斷需要防火牆規則（root）或物理拔線，而「程式裡一處 `setKeepAlive` 都沒有」這個風險**至今未被驗證**。

## 2. 槓桿：W10 剛抽出來的 ITransport

故障注入不需要虛擬機、不需要 root、不需要真實網卡——它需要的是一個可以攔截的縫，而 W10 為了可替換性剛好抽出了那個縫（`lib/transport.js`）。在那一層可以注入的東西，正好覆蓋我們想測的故障：

| 故障 | 真實對應 | 現在能不能測 |
|---|---|---|
| `blackhole` 收下但不送達、永不關閉 | 拔網路線、防火牆丟包、機器凍結 | **這就是情境 A 沒測到的那個** |
| `reset` 立即硬斷 | 關 Wi-Fi、對方進程被 kill | 情境 A 實際測到的 |
| `latency` / `jitter` | 跨機延遲、Wi-Fi 抖動 | #36 就是這一類（1500ms 寬限期在真實延遲下卡住）|
| `loss` 隨機丟 N% frame | 擁塞、弱訊號 | 未測 |
| `freeze` TCP 活著但應用層不讀 | 進程卡死、swap、GC 暴衝 | 未測，而且 keepalive 救不了這種 |
| 單向中斷 | 非對稱路由、單向防火牆 | 未測，最難用人工重現 |

## 3. 分階段

### Phase 1：`lib/transport-chaos.js`

包裝任一底層傳輸（tcp／http），由**執行期可改的控制檔**驅動（`AMCN_CHAOS=path.json`，每 200ms 輪詢），所以情境腳本能在跑到一半時翻轉故障，不必重啟任何行程。

控制檔形狀：

```jsonc
{ "mode": "blackhole",        // blackhole | reset | latency | loss | freeze | none
  "direction": "both",        // in | out | both  ← 單向中斷
  "latencyMs": 250, "jitterMs": 100, "lossPct": 5,
  "match": "127.0.0.1:47180"  // 只對某個對端生效
}
```

刻意做成獨立實作而不是改 tcp/http：`demo-transport.js` 斷言「兩種傳輸產生同一本帳」，混進故障邏輯會讓那個保證失去意義。chaos 是第三個實作，包在另外兩個外面。

### Phase 2：`lib/invariants.js`

把已經散在四支 demo 裡、各自只檢查一部分的斷言抽成可重複呼叫的函式：Σ=0、雜湊鏈可離線重驗、每筆 quorum 收據都有可歸責的 attestation、`list_verifiers` 不得包含已離線者、結算延遲上界、沒有合約卡住超過 T。

差別在**連續檢查**：現在每支 demo 在結尾檢查一次，故障情境需要的是「整個過程中不變式從未被破壞」。

### Phase 3：`chaos-run.js <scenario.json>`

一個指令跑完：拉起拓撲（Hub＋N 個 agent＋panel）→ 依時間表注入故障 → 持續取樣不變式（沿用 `drill-watch.js` 的形狀）→ 輸出時間軸報告與 PASS/FAIL。帶 `--seed` 讓失敗可重播。

首批情境，每一個都對應一個已知或懷疑的缺陷：

| 情境 | 注入 | 要回答的問題 |
|---|---|---|
| `panel-blackhole` | panel 的連線靜默中斷 3 分鐘 | Hub 多久才發現？期間 pool 是否宣告死掉的 verifier？（**keepalive 缺失的實證**）|
| `panel-freeze` | verifier 行程 SIGSTOP | TCP 活著但不回應——keepalive 也救不了，Hub 有沒有任何防線？ |
| `panel-death` | 行程被殺且不重啟 | 對應 M3 那次：確認「行程死了就不會回來」並量化後果 |
| `hub-kill-takeover` | Hub 消失 → 待命 Hub 以匯入接手 | 就是 W10 演練，但全自動、可重播 |
| `hub-blackhole` | Hub 靜默消失（非 kill） | client 端要多久才放棄那條連線 |
| `flaky-link` | 5% 丟包＋200ms±100ms 抖動，跑 10 分鐘 | #36 那一類的殘餘問題 |
| `one-way` | 只斷 Hub→panel 方向 | 最難人工重現的一種，也最容易產生「雙方都以為對方活著」|

### Phase 4：W11 紅隊接上來

紅隊盤點的 59 案裡，可自動化的 50 案大半就是故障或對手注入。`chaos-run.js` 的情境格式直接當紅隊案例的載體，`known-open` 的 13 案斷言「行為與登記簿一致」。等於 W11 不需要另一套工具。

## 4. 真實機器還是必要的——但只做它獨有的事

自動注入取代不了的：

- **跨 OS**：Windows 的 socket 行為、PowerShell 的環境變數、防火牆預設值（#32／#43 都是這條）
- **OS 睡眠與喚醒**：M3 睡著時 OS 幫忙關了 socket，這個行為模擬不出來
- **真實 DHCP 換位址**：試點中 M3 換過兩次 IP，正好驗到 discover 的價值
- **時鐘偏移**：beacon 有 60 秒容許窗，跨機時鐘要真的不同步才測得到
- **牆上時鐘 soak**：記憶體、句柄、檔案成長需要真實時間，但**不需要人盯著**

所以 W10 的 4 小時演練從「發現工具」降級為「確認工具」：所有故障先在 chaos 情境裡被找到並修好，真實演練只負責證明「在真的三台機器上也成立」。它仍然不可砍（§5），但它不該是我們第一次看到缺陷的地方。

## 5. 立即的取捨

先做 Phase 1＋一個 `panel-blackhole` 情境，因為它同時：(a) 補上情境 A 沒測到的那個故障，(b) 驗證整條工具鏈可行，(c) 大概會直接給出一個 keepalive 相關的 P1。之後再補其餘情境與 W11 對接。
