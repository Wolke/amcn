# 動態產生帶額度上限的 API key：查證計畫與結果

| 欄位 | 內容 |
|---|---|
| 文件 | 登記簿 #67 的事實查證：各家供應商是否支援「以 API 產生帶硬性花費上限的 key」 |
| 日期 | 2026-09-18 |
| 起因 | Owner 提議：常駐 agent 動態產生帶美元上限的 key，直接出借給借方 |
| 結論 | **技術面大致可行，但契約面明文禁止**。硬上限確實普遍存在（Google 甚至強制），可是第一方供應商的條款直接禁止把 key 轉給第三方——所以「上限夠不夠硬」不是決勝點 |

---

## 1. 判準：什麼情況下這個設計可行

按重要性排序，任何一項不成立就會改變整個設計：

| # | 判準 | 為什麼決定性 |
|---|---|---|
| A | **條款允許把 key 交給第三方使用** | 這是唯一無法用工程手段繞過的。上限再硬也不會讓被禁止的行為變成允許 |
| B | 上限是**強制執行**（到達即拒絕請求）而非僅告警 | 若只告警，超額風險全部落在出借方 |
| C | 上限可**按租戶隔離**（每 key／每專案），不是只有組織層 | 組織層上限無法分租——一個借方就能吃掉全部 |
| D | 上限與 key 可**由 API 設定**，不需要人進控制台 | 否則「動態出借」變成人工作業 |
| E | 可設**到期時間**，並可**事後讀取實際用量** | 出借要能收回，結算要有依據 |

## 2. 查證結果（2026-09-18）

| 供應商 | B 強制上限 | C 租戶隔離 | D API 可設 | A 條款 |
|---|---|---|---|---|
| **OpenAI** | ✅ 專案層有「Enforce a hard limit」，達標後請求回 **429** | ✅ 專案層 | ⚠️ 專案與 service-account key 可由 Admin API 建立（`POST /v1/organization/projects`），但**硬上限那個開關在 Admin API 文件裡沒有出現**——只查到控制台設定流程 | ❌ **明文禁止**：「customers cannot buy, sell, or transfer API keys from, to, or with a third party」、「You may not make account access credentials available to third parties… or resell or lease access to your account」 |
| **Anthropic** | ✅ 控制台有 workspace 花費上限 | ✅ workspace | ❌ Admin API 只有 workspace CRUD 與成員管理，**沒有花費上限端點**；`/v1/organizations/spend_limits` 僅限 **Enterprise** 組織 | 未逐條查證（見 §4） |
| **Google Gemini** | ✅ 且**強制**：分層月上限達標即暫停所有請求，無關閉選項；另有 AI Studio 的專案花費上限 | ✅ 專案層 | ⚠️ 未確認可由 API 設定 | 未逐條查證 |
| **OpenRouter** | ✅ | ✅ **每一把 key** | ✅ `POST /api/v1/keys` 帶 `limit`＋`limit_reset`（daily／weekly／monthly）——**這就是提議要的那個原語** | 其產品本身即「為每個使用者發帶上限的 key」，方向相容，但仍需逐條查證 |

**判準 B、C、D 大致成立，A 不成立**——而 A 是唯一無法工程繞過的那一項。

## 3. 因此的結論

**硬上限解決的是財務風險，不是契約風險。** OpenAI 的條款把「把 key 轉給第三方」與「轉售或出租帳號存取」分別列為禁止事項，所以即使上限完美，出借 key 本身就是違約行為。這正是 SDD 的 **P-10**（不得把禁止轉售或共享的帳戶包裝為可交易資產）與 **§16 威脅 15**（供應商封鎖疑似轉售流量）早就寫下的東西——查證的價值在於它把「原則上的顧慮」變成「條款上的明文」。

**但要誠實指出一件事：gateway 中間路線解決的是憑證問題（P-02），不是轉售問題（P-10）。** 用自己的帳號替第三方跑推理，在多數條款下仍可能構成「轉售存取」。那個問題不是這個提議造成的，它是 AMCN 這個構想本身從第一天就有的前提，而 P-10 的處理方式是要求「節點只可使用擁有者依法且依供應商條款授權的 API」——也就是把舉證責任放在節點擁有者身上。出借 key 只是**在原有問題之上再多違反一條明文的 key 轉移禁令**。

**唯一契約面乾淨的路徑**：上游是**明確支援「為每個使用者發帶上限的 key」的聚合型服務**（OpenRouter 即此類，那是它的產品功能而非漏洞）。在那種上游之下，出借帶上限的 key 可能落在條款允許範圍內——但這需要逐條讀它自己的條款，尚未做。

## 4. 還沒查證的，以及怎麼查

| 項目 | 方法 | 為什麼不能猜 |
|---|---|---|
| OpenAI 專案硬上限**是否可由 Admin API 設定** | 用 Admin key 實測 `POST /v1/organization/projects` 後嘗試設定 limit 端點；或直接讀 API reference 的 projects 子資源 | 這決定「動態出借」是否需要人工進控制台，是 D 判準的全部 |
| Anthropic 是否有非 Enterprise 的 workspace 花費上限 API | 追蹤該 feature request，並實測 Admin API | 若有，Anthropic 也進入候選 |
| OpenRouter 條款是否允許把 key 再交給第三方 | 逐條讀其 Terms 與 Acceptable Use | 這是唯一可能成立的路徑，值得讀完 |
| Google 專案花費上限能否由 API 設定 | 查 AI Studio／Cloud Billing 的 API | Google 的上限是強制的，若可 API 設定則 B/C/D 全滿 |
| 各家對「代第三方執行推理」的立場 | 逐條讀（不只 key 轉移條款） | 這關係到 AMCN 整體而不只這個提議 |

**實測必須用真實帳號做，所以要 Owner 決定是否投入**——這一節沒有做完，不是因為難，而是因為它要花錢、要用你的帳號，而且結果只有你能承擔。

## 5. 建議

1. **不要走「出借第一方供應商的 key」**——A 判準不成立，而它是唯一不能繞的。
2. 若要保留「交出一把有上限的 key」這個人機效益，走 **gateway 路線**（#67 的中間路線）：出借方本機跑 OpenAI-compatible gateway，對外發指向自己 gateway 的 key，上限與計量都在自己手上，供應商 key 永不離機。**但要清楚它沒有解決 P-10**。
3. 若真的要走「出借 key」，先確定上游是把「per-user 帶上限 key」當成產品功能的聚合型服務，並逐條確認其條款——那是唯一可能乾淨的組合。
4. 無論走哪條，**§16 威脅 2 都要重新評估**：借方送什麼內容不再由出借方控制，而帳單與法律責任仍在出借方。
