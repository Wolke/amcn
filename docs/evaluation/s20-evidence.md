## 試點規模（N=20）的證據

**一次跑完的來源**：`cd node && node chaos-run.js scenarios/soak-n20.json`（40 分鐘）。與 `soak-rebate`（N=3）、`soak-n6`（N=6）**同種子、同故障時間軸、同回流設定**，唯一的變數是交易者數量。原始 log 在 `node/out/chaos/soak-n20-*.log`，帳本在 `node/out/chaos/soak-n20-ledger.json`。

**必須先講清楚這一節不是什麼**：它是**單機 24 個行程**（20 個交易 agent、3 個 verifier、1 個排序器），不是 20 台機器。它回答「協定與帳本在試點規模上還成不成立」，**不回答**部署問題——故障域仍然只有一個，三個 verifier 同機的問題（#31）原封不動，時鐘與真實網路也沒有被測到。§20-1 的「獨立節點」證據仍然只來自那次三台機器的試點。

| 量 | N=20 實測 | 對應 §20 |
|---|---|---|
| 結算筆數 | 2,666（40 分鐘，含一次排序器 SIGKILL 與重建接手） | 2／3 |
| 七項不變式 | **零違反**，38 次取樣全部讀到帳（另 1 次 Hub 停機無帳可讀） | 4 |
| 成交率 | 0.968（2,753 得標／2,666 結算） | 10 |
| 供需深度 | 9.55 個出價／任務（**排序器觀測值**，見第 10 列） | 10 |
| 違約率 | 0（代理 0.032） | 10 |
| 平均還債時間 | 80,003 ms，127 次穿越零點 | 10 |
| 最長成交空窗 | 134 s，而那一段正是排序器停機的窗口 | 3／5 |
| 重啟後恢復 | 排序器 T+1260 重建接手，第一筆新結算 T+1291（31 秒） | 5 |
| protocol 帳戶回流 | 退還 585.62 CC，期末仍持有 90.09 CC | — |
| 記憶體 | 堆地板 10.5→18.3 MB、迴歸 0.46 MB/分；RSS **地板斜率 −1.62 MB/分**、峰值 151 MB | NFR |
| 匯出成長 | **262.2 KB/分**（協定 v5 時是 432 KB/分，`cp.heads` 移除後 −39%，見 #41） | NFR |

**這一節推翻或修正了三件先前寫過的事**：

1. **「最長空窗隨 N 改善」是誤讀**。183 s（N=3）→ 131 s（N=6）看起來像 N 的效果，而 N=20 三輪都落在 131–134 s，且那一段就是排序器停機的窗口——**那個數字量的是故障時間軸，不是市場**。
2. **總量信用使用率不是「會不會鎖死」的指標**。它隨 N 下降（52.0%→36.0%→29.1%），但同一輪有 **10/20** 個 agent 曾貼到自己額度的 90% 以上。差別來自分母被結構性順差者**沒用到的**額度灌大：一個 agent 期末 +659 CC、峰值負債只有 16.3／額度 493。逐帳戶的峰值分佈才是該看的東西（#61）。
3. ~~**提高 N 沒有解決吸收端，只是換了一個**~~ **這一條在四小時的尺度上被推翻了，見下一節**。40 分鐘量到的是「非交易角色佔正餘額 97.5%（N=6）→ 46.0%（N=20）」，看起來像 N 稀釋了吸收；**四小時之後這個數字是 100.0%**——交易 agent 手上的正餘額歸零。所以 46% 不是一個性質，是一個**還沒跑完的過程**的中途值，而所有 ≤40 分鐘的長跑都系統性低估它。

**同種子四輪的離散**（這些數字要當區間讀，不是點估計）：結算 2,574／2,915／2,823／2,666；期末使用率 28.9／32.3／30.9／29.1%；曾貼上限（≥90%）9／10／10／10 of 20；非交易角色佔正餘額 44.7／41.2／43.1／46.0%。

## 四小時耐久（單機，2026-09-20）

`cd node && node chaos-run.js scenarios/soak-4h.json`。N=20、14,400 秒、兩次排序器 SIGKILL 與重建接手。**7/7 PASS，13,026 筆結算，七項不變式零違反，114 次取樣全部讀到帳。**

**再強調一次它不是 W10 的拔線演練**——那需要多台真實機器。這是單機的耐久面，而 #74 與 #41 都點名「這個量級從未被觸及」。

### #74／#41 的推估全部兌現

| #74 當初的推估 | 四小時實測 |
|---|---|
| 「四小時後匯出約 50MB」 | **51.1 MB** |
| 「100 KB/s 的預算會把快照間隔拉到約 8 分鐘」 | **523 s（8.7 分）**，尾檔因此保存 0.9 MB 的歷史 |
| 「大尾檔重播從未在那個規模被測過」 | 第二次重啟重播並驗證 **11,532 筆收據／12,683 個 checkpoint，簽章與鏈全部通過**；`noHistoryLoss` 實測殺掉當下 11,504 → 期末 13,026，指定的 `contract_id` 仍在帳上 |
| #41 的 16MB frame 上限 | 匯出在第 ~75 分鐘跨過，之後**每一次取帳都是分頁**——114 次取樣全部成功，最大約 52MB。#81 的凍結快照在這個量級撐住了 |

### 記憶體：沒有洩漏，但**活躍集本來就會長**

RSS 地板斜率 **−0.10 MB/分**（峰值 241MB），所以沒有洩漏。但堆地板從 16.1 MB 長到 **43.9 MB**，而那是真實的活躍集成長：保留狀態同期從「事件 579／鏈分錄 2,324」長到「**事件 14,283／鏈分錄 99,196**」。**排序器把全部歷史留在記憶體裡**，所以記憶體隨歷史成長是設計使然而非缺陷——但這代表「跑多久」而不是「跑多大」才是它的上界，值得在真正的長期部署前有個答案。

### 最重要的一件事：#62 是**時間**的函數，不是 N 的函數

| | N=6／40 分 | N=20／40 分 | **N=20／4 小時** |
|---|---|---|---|
| 非交易角色（verifier）佔全部正餘額 | 97.5% | 46.0% | **100.0%** |
| verifier 絕對持有 | 210 CC | 560 CC | **2,602 CC** |
| 交易 agent 持有的正餘額 | — | 659 CC | **0.00 CC** |
| 信用使用率（期末／峰值） | 36.0% / — | 29.1% / 36.4% | **53.0% / 66.0%** |
| 曾貼上限 ≥90%／≥99% | 1/6 / — | 10/20 / 0/20 | **14/20 / 4/20** |

四小時之後**沒有任何一個交易 agent 是淨債權人**：最高的三個是 −20.64、−25.68、−36.15，最低的是 −493.82（額度 500）。全部 2,602 CC 的正餘額在三個 verifier 手上。

這推翻了先前「提高 N 稀釋了吸收端」的讀法。verifier 賺驗證費而**永遠不買東西**（FR-056 的「正餘額無處可花」），所以那是一個**單調的抽取**；N 只影響速度，不影響終點。40 分鐘的 46% 是過程中的一個切片。

**對 §20 的影響**：十項驗收沒有一項因此失敗——閉環仍然閉合、帳仍然守恆、指標仍然算得出來。但 §5 的「經濟閉環」在四小時尺度上**依賴 #62 被解掉**，而 #62 選定的修法（(a) 讓 verifier 也參與市場）尚未實作。這是目前為止對那個修法最強的證據，也說明它不能再延。

## #62 階段 4：把驗證變成角色，吸收端會不會消失（2026-09-20）

`node chaos-run.js scenarios/soak-4h-dual.json`，與上一節的 `soak-4h` **同種子、同故障時間軸、同預算、同期望**，唯一的變數是 **20 個雙角色節點** 取代「20 個交易者＋3 個純 verifier」。兩邊都 **7/7 PASS**、不變式零違反。

|---|---|---|
| 結算筆數 | 13,026 | **15,733（+20.8%）** |
| 正餘額總額 | 2,602.11 CC | **2,102.39 CC（−19.2%）** |
| 由誰持有 | 三個 verifier，**100.0%** | 交易 agent **100.0%**——但其中 **C 一人持有 2,102.39，也就是全部** |
| 第二高的帳戶 | 全部交易 agent 皆為負 | **A −0.52**（同樣是負的） |
| 信用使用率（期末／峰值） | 53.0% / 66.0% | **40.8% / 54.4%** |
| 曾貼上限 ≥90% | 14/20 | **13/20** |
| 曾貼上限 ≥99% | 4/20 | **8/20（更差）** |
| 最長空窗 | 261 s | 263 s |
| 成交率／供需深度 | 0.993 / 9.5 | 0.958 / 9.51 |
| 匯出成長 | 51.1 MB｜212.8 KB/分 | 71.4 MB｜287.0 KB/分（成交量較高） |
| RSS 地板斜率 | −0.10 MB/分 | −0.18 MB/分 |

### 結論：(a) 是**必要但不充分**

**它確實移除了「物種級」的吸收端。** 純 verifier 那一輪，三個不交易的帳戶把全部 2,602 CC 抽走且永不回流；雙角色這一輪沒有任何非交易帳戶，流通量因此多出 20.8% 的結算、正餘額總額少了 19.2%、信用使用率從 53.0% 降到 40.8%。這些都是真的改善，方向與 #62 選 (a) 的理由一致。

**但經濟的終局形狀沒有改變：仍然是一個帳戶持有全部正餘額。** 只是那個帳戶從「三個 verifier」換成「一個交易 agent（C）」。而 C 的峰值負債只有 **11.2 CC／額度 500**——**它幾乎沒有買過東西**，行為上與 verifier 無異。換句話說：

> 把驗證變成角色，解掉的是「這個角色在設計上不消費」；沒有解掉的是「**這個參與者在需求上不消費**」。後者就是 #64 的結構性順差者，而它需要另一支槓桿。

**一個變差的指標值得記下來**：曾貼到自己額度 ≥99% 的節點從 4/20 變成 **8/20**。總量使用率下降的同時個別貼牆變多，成因與 #61 記的同一件事——總量被結構性順差者沒用到的額度稀釋，而赤字端反而被抽得更緊（雙角色下驗證費也流向 C 這種淨賣方，加速集中）。

### 留存率：兩個吸收端的機制其實完全不同

期末分佈看起來一樣（都是一個帳戶持有全部正餘額），但**逐帳戶的留存率＝淨額÷流入**把它們分開了：

| | 收 | 付 | 留存率 |
|---|---|---|---|
| 純 verifier（三個，四小時） | 859 CC | **5 CC** | **99.4%** |
| 雙角色的累積者 C | 8,840 CC | 6,809 CC | **23.0%** |
| 全體中位數（雙角色） | — | — | **−22.9%** |

verifier 幾乎**不花錢**（收 859 付 5），那是設計使然；C 把收到的 **77% 都花掉了**，它的集中來自**吞吐量不對稱**——它的流入是赤字端（1,489–3,469 CC）的三到六倍。

**這改變了該用哪一支槓桿**。保管費（#66）打的是**存量**，對 99.4% 留存的 verifier 對症；但對 C 這種「高吞吐、留存 23%」的參與者，存量費要抽乾它就得追上它的淨流入速度，而那是**流量**問題。與之相稱的是：對淨流入課費（交易連動）、或讓 Treasury 把 CC 送回赤字端、或直接處理 #64 的需求／容量失配。

**一個單位陷阱要寫下來**：我原本想用 C 的收入率去錨定 #66 掃描的 %/天 費率，算出來是 **615.80%/天**——那不是結論，那是**單位錯誤**。原型的經濟時鐘比模擬器快約兩個數量級（需求每 900 ms 一跳，模擬器是 84 天），所以「%/天」在兩邊不是同一個單位。**留存率是無因次的，因此是目前唯一能直接跨兩個模型比較的量**，`chaos-run` 的人口報表現在固定輸出它。

**對 §5 的意義**：四小時尺度的「經濟閉環」**仍未成立**，但瓶頸已經從 #62 移到 #64／FR-056。#62 的 (a) 應該收尾（它有正面效果且已實作到階段 3），而下一支槓桿要從 §2.2 設計的 Treasury 支出側（金絲雀、逆週期收購、L_boot 補貼）或 #66 的保管費裡選——後者在模擬器裡掃過，結論是「費率必須超過累積者的收入率才抽得乾」，而 C 的收入率現在有實測值可以對照。

## #38 押注沒收與退還：一個 2×2，不是一條規則（2026-09-22，原型）

模擬器在 2026-09-21 量到逃逸路線：偷懶的 verifier 只要**每 2 天換一次身分**，就能在金絲雀樣本累積到證據門檻之前把押注留在舊 DID 上，淨收益與誠實者相同（47.01 對 47.39）卻完全不用做事。修法是一條規則而不是一個費率——**未達 `slash_min_samples` 就棄置身分時，已託管的押注不退**。

**做原型時發現登記簿漏了一半。** 原型的押注從前只進不出（託管 → 罰沒），所以「不退押注」在原型裡是**純記帳**：那筆 CC 早就不在 verifier 的餘額裡，沒收與不沒收對離開的人一模一樣。嚇阻要成立，必須存在**拿得回來**的情形——於是同日補上 `stake_release`（協定 v6 → **v7**）：被測夠且失敗率過關者可取回，**取回即退出 pool**。

閘門是 `node demo-forfeit.js`（約 70 秒，14 項斷言）：**14/14 PASS**。它測的是一個 2×2：

| | 被測夠（樣本 ≥ 5） | 沒被測夠（樣本 < 5） |
|---|---|---|
| **離線** | 押注留在託管、未被沒收（0.2437 → 0.2437）——**退出不是規避** | **全額沒收 0.0217 CC 轉入保險池** |
| **在線** | **可取回 0.2851 CC 回到自己的餘額（餘額 +0.4489），並退出 pool** | 取回請求 3/3 被拒、押注只增不減——**沒被測到不是罪，但也不能提前抽走** |

四格缺一格都會讓規則變成別的東西：只有左上就是「押注等於罰金」，只有右下就是「沒被測過的人自由提領」，而沒有左下（可取回）那一格，沒收就只是搬帳。

**退還自己帶出一條比 #38 更省事的攻擊，而第一版實作是通的。** 取回押注之後只要**斷線重新註冊**，就能帶著乾淨的受測紀錄（樣本 12、零失敗）回到 pool，而身上押注是 0——被金絲雀抓到也罰不到東西，連換身分都不必。第一版把「已退出」旗標掛在 agent 記錄上，而 `register` 會整筆換掉那筆記錄，所以重連就清乾淨了。修法：退出的身分記在一個獨立的集合裡，**並且可由事件流重建**（匯入時掃 `stake_release` 事件），於是 **取回押注 ＝ 結束這個 DID 的驗證生涯**。要再驗證就得用新身分——沒有受測紀錄，並重新暴露在沒收規則下。閘門第四階段實測：V1 取回後重新註冊，pool 仍然只有 V3／V5／V6。

**唯一不該存在的組合是「乾淨的受測紀錄 ＋ 身上零押注」**，而上面三件事（沒收、退還、退出即永久）合起來就是在守這一句。

**對帳**：`stake_forfeit` 事件的保險池分錄總額 ＝ `canary_stats.forfeited_cc` 的歸屬總額 ＝ 0.0217 CC；Σ=0 在沒收與退還之後成立；`protocol:stake` ＝ 各自持有額之和（1.8733）；**獨立重建路徑同意這本帳**。重建另加一條檢查：`slash` 與 `stake_forfeit` 的事件總額必須各自等於其歸屬欄位——只比總和的話，把一筆沒收改記成罰款不會被發現，而那會把一個早退者寫成作弊被罰的人。這一條有自己的竄改負對照（總額不變、Σ 不變，重建仍拒絕）。

**紅隊兩案**（`redteam.js` 45 案，S19／S20）：非 verifier 的取回請求被指名拒絕；一個**簽章完全有效**的退還請求從別的連線送出時押注分文未動（0.0713 → 0.0713）——後者是 #53 那一類的形狀，簽章有效但發話的連線不是那個身分。

**「取回之後押注又長回 0.1639」是正確的，不是漏洞**：退出只對**新的** pool 生效，已經在飛的合約仍會結算、驗證費照樣託管。斷言因此比的是「現有押注 ＝ 取回之後才發生的託管」。

**閘門自己寫壞過三次，而三次都值得記下來**：(a) 寫死「殺 V4」，但 panel 是每筆合約從池子推導的，那一次剛好每次都抽到 V5，於是 V4 押注是 0——**關鍵三條斷言全部在空資料上「通過形式」**（6/9，而失敗的三條看起來像功能沒做）。(b) 流量寫成「一買一賣」，買方 22 秒把額度用光（全程 6 筆收據），晚到者根本進不了 panel——CC 要循環才有持續的驗證費。(c) 斷言「取回後押注必須為 0」，把上面那個正確行為判成 FAIL。三次都同一個形狀：**閘門的前置條件自己沒有被斷言**，所以現在受害者是從帳上挑的，而前置條件本身就是頭兩條。

**這一節不宣稱的事**：門檻在生產預設是 14 天（`HUB_STAKE_FORFEIT_AFTER_MS`，同違約門檻），閘門把它壓到 4 秒。「14 天離線 ＝ 丟掉身分」這個判斷沒有真實數據，它與 `HUB_DEFAULT_AFTER_MS` 共用同一個未經驗證的假設。另外，「取回即永久退出」是**原型的選擇，不是模擬出來的結論**：它關掉了「乾淨紀錄 ＋ 零押注」那個組合，代價是一個誠實 verifier 想拿回自己的 CC 就得放棄聲譽。這個代價對供給端的影響沒有被量過——模擬器裡 verifier 不會「收工」。

## 第一次有人從網際網路加入（2026-09-22，#89／#86）

在此之前，這個網路的每一次連線都在同一個區網裡。這一節記的是第一次不是。

**做法不是把機器掛上公網**，而是換一個傳輸：`AMCN_TRANSPORT=tor`。Hub 仍然只聽
`127.0.0.1`（**對外零入向埠**，實測從本機區網位址 `192.168.50.30:47180` 連不上），
由 onion service 的 rendezvous 把外面的人帶進來。不開埠、不動路由器、不租機器。

這件事之所以必要，是因為開發機所在的網路**根本不可能** port forward：ASUS 路由器
的 WAN 是 `192.168.1.103`（私有位址，雙層 NAT），上游那台沒有 UPnP、web 介面也
不回應。而那不是一個罕見的處境——它就是一般家用網路。

### 量到的

| 項目 | 數字 |
|---|---|
| onion 位址 | `o344qap4…u5yd.onion`（56 字元的 v3 位址，本身就是 ed25519 公鑰） |
| 第一次取帳（含建電路） | **9.15 s**，131.8 KB、366 個 checkpoint |
| 之後三次取帳 | **2.48 / 2.55 / 2.57 s**（同樣 131.8 KB） |
| 帳本驗證 | `verify-ledger.js --pin did:demo:634d724a19976c95` **通過**，Σ=0 |
| verifier 註冊 | 送出到 Hub 記錄之間 **約 2.1 s**（10:33:45 → 10:33:47） |

### 最重要的那一行

一筆**真的結算**，而它的 panel 裡有一位 verifier 全程走 tor：

```
SETTLED(dual) c-t-wan-buyer-8fbb5010-…: 買方=-10.00 賣方=+8.75
   protocol:treasury=0.25 protocol:insurance=0.60
   did:demo:52055d85b=0.13  did:demo:4385c2f5b=0.13  did:demo:e196d19a1=0.13
```

`did:demo:e196d19a1` 就是那個 tor 客戶端：它收到 verify_request、跑完斷言、送出
承諾雜湊、揭示裁決、拿到 0.13 CC 的分潤——全部經由一條 tor 電路，而 Hub 沒有開
任何對外埠。之後買方又供給三次工作把負餘額還掉（−10.00 → +3.78），所以帳上沒有
留下任何無人償還的洞。

### 不宣稱的事（這一節很容易被讀成比它更強）

- **兩端仍然是同一台機器**。流量確實走出去經過 tor 的中繼再回來（rendezvous 與
  NAT 穿透是真的被用到了），但「兩台在不同地點的機器」還是零次。#86 因此只被
  部分關閉：可達性解決了，**地理與故障域的獨立性沒有**。
- **仍然是同一個 owner**，所以市場數字照舊是關聯方（#63）。
- **延遲的代價是真的**：2.5 秒取一次帳在互動式使用上是可接受的，但那是 131.8 KB
  的匯出；長連線的穩定度（電路重建、`AMCN_IDLE_TIMEOUT_MS` 要不要放寬）還沒量過，
  長跑情境也還沒在 tor 之下跑過。
- **tor 本身是一個依賴**。零相依那條原則指的是 npm／pip，不是「不需要任何外部
  軟體」；`AMCN_TRANSPORT=tor` 需要兩邊都有 tor，而預設的 `tcp` 不需要。

## 「額度只能賺」的第一輪證據（2026-09-22，#90）

Owner 否決了擔保人架構（「網路上都是匿名的誰可以替誰擔保？agent 要怎麼幫另一個
agent 擔保」），而那個否決是對的。取而代之量的是另一條：**不要送額度，Treasury
去買新人的第一份工作**。

### 三組對照（200 agents × 56 天 × 3 種子，baseline）

| | 結算量 | 成交率 | 壞帳 | 入門採購 |
|---|---|---|---|---|
| A 送額度 `starter=20`（現況） | 3,995.7 | 0.928 | 81.9 | — |
| B 零額度、什麼都不做 | **666.1**（17%） | 0.814 | 0 | — |
| C 零額度＋入門採購 20 | 2,937.3（74%） | **0.936** | **1.0** | 3,941 |

B 那一行是整件事的支點：**「乾脆不給」會把市場殺掉**（結算量剩 17%），所以
bootstrap 問題是真的，不是理論上的顧慮。C 拿回 74% 的量，而成交率反而最高——
因為付不出錢的需求不會變成掛在那裡沒人接的任務。

### Sybil：一個攻擊者 20 個身分

| | 每身分白拿 | 沖銷總額 | 壞帳率 |
|---|---|---|---|
| A 送額度 | **17.49 CC** | 349.8 | 9.25% |
| C 零額度＋入門採購 | **0.00 CC** | 0.0 | **0** |

白拿**不是變小，是歸零**：那份無擔保的禮物就是整個攻擊面（#50 量到的 45.86
CC／身分正是它）。N 個身分要拿到 N 份 CC，就得交付 N 份真實工作。

### GATE-0：6/8 → 加上 `--dual-role` 之後 8/8

首跑（`--starter 0 --onboarding 20 --onboarding-total 40000 --risk-thin 0.06
--risk-base 0.02`）**6/8**：G8 verifier 留存 100% 全敗。加上 `--dual-role` 後
**8/8**，G8 留存 10.4–24.6%——所以那個 100% 是「verifier 是另一個物種、在模型裡
沒有需求」的產物，不是機制問題。成本：500 個身分／84 天共 **9,884 CC**
（每人 19.8，上限綁住）。

### 但 8/8 有兩件閘門看不到的事，而它們比分數重要

**(1) G2 的通過是空的。** 四個情境三個標「不適用」，wash_heavy 只有一個種子可評。
它比的是「洗量者的額度 vs 同活躍度誠實者的額度」，而後者是 **0.0**——零額度體制
下沒有任何誠實帳戶達到可比的量，所以那條判準**量不到東西**。洗量者的額度收在
13.9 CC 看起來很好，但那不是 G2 驗出來的。

**(2) 洗量佔成交量從 40.3% 升到 66.3%**（wash_heavy、300 agents、56 天、2 種子）。
拆開來看不是洗量變多——**洗量幾乎沒動（9,657 → 9,828）**，是**誠實量塌了**
（14,281 → 5,002）。原因很直接：**洗量者不需要信用**，它們把手上的 CC 在自己
之間轉圈就好；誠實的買方需要信用才買得下去。所以零額度對誠實買方比對洗量者更狠。

壞帳換來了（58.1 → 0.0），代價是**可見成交量裡有更大一塊是洗量**——而那正是 #63
的同一個教訓：**成交量不是需求的證據**。處置是報告紀律，不是回去送額度。

### 「通過驗收才付」之後，漏水的地方不是我以為的那個

模擬器改成「與普通結算走同一條驗收路徑」（真值 = reliability × quality 的抽樣，
而網路依據**面板的裁決**）之後，量到的第一件事是**面板是準的**：整場 1128 次裁決，
真值為 True 945 次、面板判 PASS 943 次——誤差 2/1128。四組對照也證實同一件事：

| 設定 | 攻擊者每身分領到 |
|---|---|
| 預設（6 verifier、無偷懶） | 5.52 CC |
| 面板加倍（12 verifier） | 5.30 CC |
| 兩成 verifier 偷懶 | 5.37 CC |
| 金絲雀率 3% → 10% | 4.67 CC |

幾乎不動，所以**漏水不是驗證誤判**。真正的形狀是：交假東西的攻擊者（品質 0.1、
產能 40u）**每個身分矇中一次就拿到 4 CC**，然後才被三次失敗踢掉。身分免費，
所以那是 N × 4 CC 的線性漏水。

### 失敗上限是錯的旋鈕，連續通過才是對的

| 失敗上限 | 攻擊者每身分 | 誠實新人（總額／人數） | 誠實每人 |
|---|---|---|---|
| 1（一次出局） | 4.89 CC | 2746.2／**174.3** | 15.8 |
| 2 | 4.22 CC | 3584.0／194.7 | 18.4 |
| 3 | 5.52 CC | 3761.3／196.0 | 19.2 |

**一次出局沒有讓攻擊者拿得更少**（4.89 vs 4.22，差距落在種子離散內），卻讓 200 人
裡 26 個誠實新人進不了門——誠實交付的失敗率是 10.6%，一次不走運就永久排除。
它限制的是「失敗幾次」，限制不了「矇中幾次」。

| 要求連續通過 | 攻擊者每身分 | 誠實新人（總額／人數） | 誠實每人 |
|---|---|---|---|
| 1 次 | 5.52 CC | 3761.3／196.0 | 19.2 |
| 2 次 | **1.33 CC** | 3387.5／191.7 | 17.7 |
| **3 次** | **0.00 CC** | 3011.3／187.0 | 16.1 |

對攻擊者是平方壓制、對誠實者幾乎無感（0.095³≈0.0009 對 0.9³≈0.73）。**預設定為 3**：
那 9 個沒領到的是品質低到連續三次都過不了的節點，而「連續交出三份通過驗收的工作」
正是「證明你做得出來」本身，不是誤殺。

GATE-0（`--dual-role`、連續 3 次）**7/8**，而第八條是 G2「量不到」而不是「沒過」
（四個情境全部不適用，理由同上一節）。

### 原型同步：發樁者連失敗也要報上來

連續次數由 **Hub 自己數**，所以發樁者必須把每一次的實際裁決都報上來
（`report.outcome`，與「正確答案是什麼」的 `expected_verdict` 是兩件事）——只報成功
的話 Hub 永遠算不出連續，那個旋鈕就不存在。`HUB_ONBOARD_STREAK` 預設 3。
閘門 `demo-onboard.js` **10/10**，其中兩條是這一輪加的：「要連續 N 次才付一次」
（實測 3 次付款，一次一付會是 6 次）與「交付未通過時連續次數歸零」。

**信任邊界**：發樁者是營運方授權的身分，所以它**能夠多報失敗來卡住某個新人**。
那個權力本來就存在（它也可以乾脆不發任務給你），制衡是它的支出全部在帳上、
可稽核、有治理上限。

### 採用這個方向的兩個條件

1. **入門採購買的必須是答案已知、可驗證的工作**（金絲雀的同一個機制）。模擬裡
   Treasury 只是消耗掉對方的產能；真實版本若買的是做工給你看的東西，攻擊者就是
   每身分白拿 20 CC，只換了記帳名目。這樣攻擊成本才等於真的做那份工作的成本，
   而防線退回「驗證會不會被騙」——那是這套設計本來就在守的東西。
2. **§20-9／§20-10 的成交量必須把洗量與關聯方分開列**，否則零額度體制下的量比
   現在更容易被誤讀。

## 結論

**2026-09-19 更新**：十項裡 **9 項有完整的自動化證據**，1 項部分（#6 的 sandbox 面）。與 2026-09-17 相比，項數沒變，但**證據的性質變了三處**，而三處都是往「少宣稱一點」的方向：

1. **§20-10 的宣稱被下修**（#77）。原本寫「四項全部由簽署狀態導出」，那對**供需深度**是過度宣稱——只有排序器看得到所有出價。現在分三層並寫進匯出的 `provenance` 欄位，見該列。
2. **§20-4 的重建在一次尾檔恢復之後曾經不成立**（#78）。`at` 只存在於鏈分錄、events 沒有時間欄位，而尾檔當時不帶鏈分錄，所以恢復後重算出的 root 對不上任何一個已簽署的 checkpoint，`rebuild()` 卻回報 ok。已修並補上「root 必須概括重建出的 chain heads」這條檢查；負向對照會讓 Hub 拒絕啟動。
3. **§20-5 的「可恢復」多了一個前提**：取帳本身不能依賴帳本大小。匯出超過單一 frame 時從前是**靜默斷線**（#76／#41），現在是指名的拒絕＋游標分頁，`ledger-dump.js`（災難恢復工具）已改走。

**兩個缺口的性質不同**：

- **§20-6 的 sandbox 面是架構上還不存在**（盤點 §3 列為原型不可達）。Phase 1 無法補齊，只能誠實標註。
- **`related-party` 是自行申報的**，Hub 無從查核兩個 DID 是否同一個 Owner（#63）。§20-9 因此在「可區分」這件事上**只對誠實者成立**，這句話必須進報告。

**規模上的誠實限制**：下文 N=20 那一節是**單機 24 個行程**。它回答的是「協定與帳本在試點規模上還成不成立」，**不回答**「20 台機器的部署」——後者的故障域、時鐘、網路都不同，而 #31 已記下三個 verifier 同機即同一故障域的問題。

## 建議順序

0. **找一個真的外部參與者**（Owner 於 2026-09-22 決定開始推廣）。這已經是唯一還在
   binding 的限制：§20 十項裡 9 項有自動化證據、45＋13 案紅隊全過、三台真機試點跑完，
   但**帳上每一筆都是同一位 owner 的關聯方交易**（#63），所以「有人願意付錢」這件事
   零證據。程式面的入口這一輪補齊了（#84）：`quickstart.sh` 單機起一個真網路、
   `node/JOIN.md` 可直接轉給人、身分 seed 變成預設、`verify-ledger.js` 讓對方能自己驗帳、
   `pilot-doctor.js` 在別人的機器上不再說謊。**第一個外部參與者要量的東西**：他有沒有
   真實需求（不是我們給的任務）、他的額度成長曲線、他會不會在 30 天的年齡斜坡走完之前
   放棄、以及第一次真正的「陌生人之間」結算。

2. **多機的 N=20**：把單機 24 行程的結果搬到真實機器，才對得起 §20-1 與 #31。
3. **§20-6 sandbox 面**：Phase 2 範圍，本階段只標註。
